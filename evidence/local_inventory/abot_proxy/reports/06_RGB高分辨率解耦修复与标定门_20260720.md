# ABOT-X4 Gemini RGB 高分辨率解耦修复与标定门（2026-07-20）

> 当前结论：**`1280×720@30 MJPEG` 的解耦 RGB-D 工程链已修复并通过无运动现场测试，但只使用临时几何拟合与工厂外参，尚未通过物理标定和 0.3/0.5/0.8 m 三维精度门。真机收尾仍运行 `640×480@30` 基线。**

## 1. 为什么旧链路会崩

旧 `gemini.launch` 只把 RGB 宽高改为 16:9 高清档，却仍由 UVC 驱动把工厂 `640×480` 的 `K/R/P` 写进新的 CameraInfo。`rgb_rectify_color` 随后按不一致的尺寸和几何执行 OpenCV ROI，触发 `rowRange` assertion；RGB、Depth 和注册点云共用同一个 nodelet manager，因此整个深度链也被一起带崩。

这不是内存不足，也不是“720p 本身不出流”。七档旧测试已经证明 720p RGB 可达 30 FPS，失败发生在共享注册/校正链。

## 2. 正式修复架构

```text
1280×720 RGB + mode-specific CameraInfo
                    │
          YOLO/VLM bbox in RGB pixels
                    │
640×400 raw depth point cloud
camera_depth_optical_frame
                    │ factory R,t (provisional)
                    ▼
camera_rgb_optical_frame XYZ
                    │ project with 720p K
                    ▼
       bbox depth cluster median
                    │
                    ▼
/target_point (PointStamped)
camera_rgb_optical_frame
```

实施点：

- `gemini.launch` 新增 `rgb_width/rgb_height/rgb_frame_rate/rgb_video_mode` 参数，默认仍为 `640×480@30 MJPEG`。
- UVC 驱动在 camera_info_manager 中存在且尺寸匹配时保留该档标定，不再被工厂 640p 数据覆盖。
- 720p launch 关闭 `depth_registration`、`depth_registered_processing` 和软/硬注册处理，保留 `/camera/depth/points`。
- 定位器新增 `point_cloud_frame`、`depth_to_rgb_rotation`、`depth_to_rgb_translation`，将原始深度点云刚体变换到 RGB 光学坐标后再用 720p `K` 投影。
- 对 CameraInfo 主点、焦距、有限值和外参旋转正交性做失败关闭检查。

## 3. 当前标定数据的可信度

### 720p 内参：临时可测试，不可交付机械臂

当前 `gemini_rgb_1280x720.yaml` 来自同一 Gemini 的 640p 工厂内参与跨分辨率 SIFT/仿射拟合：

- 487 个 homography 内点；
- 中位重投影残差约 `0.345 px`；
- 720p 相对 640p 近似为 2 倍缩放，再做约 120.6 px 的垂直中心裁切。

这足以验证软件几何和时间同步，但不是棋盘格/ChArUco 物理内参标定。

### 深度到 RGB 外参：工厂值换向

当前外参由设备服务给出的 `R_right_to_left` 与平移换算为 depth→RGB：

- 平移约 `[9.982, -0.055, 0.755] mm`；
- 旋转矩阵通过正交和 `det(R)=+1` 检查。

仍须用实体标定板或精密靶标做外参优化和独立验证。

## 6. 已部署的无界面标定与精度门

### 6.1 720p RGB 内参标定

`calibrate_rgb_intrinsics.py` 订阅 `/camera/rgb/image_raw`，只接受 `1280×720`，自动检测棋盘格并拒绝重复姿态。默认合同：

- 棋盘格为 `8×6` **内角点**；
- `square_size=0.03` 只是 30 mm 方格示例，运行时必须填实体方格的实测边长；
- 需要 25 个分布不同的视角；
- `RMS ≤0.5 px`、单视图重投影误差 P95 `≤1.0 px`；
- 棋盘中心横纵覆盖跨度均 `≥25%`，尺度跨度 `≥5%`；
- 任何门失败只写 JSON 报告，不写 CameraInfo YAML。

相机栈必须是单实例；先停止 640p 基线并确认旧相机进程退出，再运行：

```bash
export CAMERA=gemini
source /opt/ros/melodic/setup.bash
source /home/abot/catkin_ws/devel/setup.bash
roslaunch vl_locate calibrate_720p_intrinsics.launch \
  board_columns:=8 board_rows:=6 square_size:=0.030 required_views:=25
```

默认候选结果只写入 `/tmp/gemini_rgb_1280x720_calibrated.yaml`，报告写入 `/tmp/gemini_rgb_1280x720_calibration_report.json`。必须先审核报告和实体尺寸，备份旧 YAML 后才允许替换项目配置；工具不会自动改正式配置。

### 6.2 三维精度统计

`checkerboard_bbox_publisher.py` 从 720p RGB 自动检测 `8×6` 内角点，以原图 Header 发布类别 `checkerboard` 的 YOLO 兼容 bbox；尺寸不符或检测失败时不发布。`rgbd_accuracy_gate.py` 只做评估，订阅 `/target_point`，不发布控制命令。每个距离独立运行：

```bash
roslaunch vl_locate checkerboard_720p_accuracy.launch \
  expected_x:=0.000 expected_y:=0.000 expected_z:=0.300 \
  rgb_camera_info_url:=file:///tmp/gemini_rgb_1280x720_calibrated.yaml \
  output_path:=/tmp/rgbd_checkerboard_accuracy_0300.json
```

`expected_x/y/z` 必须来自实体治具或独立测量；只有靶心确实与 RGB 光轴重合时才能把 `x/y` 设为零。依次在 `0.3/0.5/0.8 m` 采集，要求每档有效率 `≥90%`、三维欧氏误差中位数 `≤20 mm`、P95 `≤40 mm`。检测器、定位器和评估器必须保持单一检测源，且 `/target_point` 无任何运动消费者。

现场已验证失败关闭行为：

- 当前 640p 基线上运行 720p 标定器，会明确报告尺寸不匹配，超时后 `passed=false`，且不生成 YAML；
- 无检测输入时精度门记录 `attempts=0`、`passed=false`，空指标使用 JSON `null`，可被严格 JSON 解析器读取；
- 棋盘格 bbox 发布器在当前 640p 基线上明确拒绝尺寸不匹配，探针结束后 `/yolov5/BoundingBoxes` 无发布者；
- 两个探针结束后 ROS graph 只剩原 Gemini 相机栈与 `rosout`。

## 8. 受控使用命令

只做相机/接口验证：

```bash
export CAMERA=gemini
source /opt/ros/melodic/setup.bash
source /home/abot/catkin_ws/devel/setup.bash
roslaunch vl_locate gemini_720p_rgbd.launch start_localizer:=false
```

只有在完成物理标定并复核无运动消费者后，才可启动定位器：

```bash
roslaunch vl_locate gemini_720p_rgbd.launch \
  start_localizer:=true source_mode:=yolo
```

`1080p25` 与 `1440p15` 不得直接照抄 720p YAML；每档必须拥有自己的 CameraInfo、实际 FPS/同步验证和三维精度门。按项目目标，只有 720p 物理精度门通过后才进入 1080p，1440p 最后处理。
