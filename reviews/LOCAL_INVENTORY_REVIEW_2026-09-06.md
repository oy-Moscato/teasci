## 2. 汇总可复算与算法重现必须分开

`final_30frames.json` 有30次尝试、29次接受；接受记录的29个时间戳唯一，跨度约50.986秒。这批数据使用同一组人工审计的四个像素关键点。它与另一份30角度云台扫描清单是不同采集记录，不能把29/30理解成30个视角的发现成功率。

方向计算先统一轴向符号，再取平均单位轴，最后计算各帧相对平均轴的夹角。方向即使整体有固定偏差，也可能得到很小的帧间离散。因此1.008°支持该记录中的输出稳定性，不能作为茶芽姿态绝对误差。

本轮还用保存的四个三维点调用当前上传的 `fit_oriented_axis()`，作了更靠前一层的复核：

- 按现场脚本默认拟合阈值0.020米，有1/29帧不同。记录 `index=7`（从0编号的第8次尝试）的重新拟合方向与保存方向相差约13.0476°；残差第95百分位从保存的5.1574毫米变为1.4494毫米。
- 按几何函数自身默认阈值0.015米，有15/29帧不同。
- 原报告所记 `stem_axis_geometry.py` 哈希为 `8e7c692a…`，上传文件是 `cfee8bbc…`；将上传代码统一为两种常见换行后，仍不匹配历史哈希。

所以可以说“保存轴向和残差的汇总已复算”，不能说“原始点云到结果已逐步复现”。以上两组阈值分别来自当前函数和脚本默认值，不是找回了当时启动参数；差异可能涉及实现版本、实际参数或数值择优分支。下一步只需定点找报告所记哈希对应的旧代码及实际启动命令、依赖版本，不通过反复调参追平历史结果。

此外，唯一失败记录是 `index=12`，缺支持深度簇的位置为 `(240,380)`，对应第4个审计点。原报告称第1点失败，与结果文件不一致。保留报告原件，在后续失败分析中采用可追溯的第4点记录。

## 3. 数据同步与场景标签的新发现

六条彩深节选的时间差依次为47.631、44.809、42.392、14.812、13.005、11.441毫秒，均标为 `qc_pass=true`。它们使用 `system_timestamp_nearest`，即按系统时间戳最近匹配；这不是硬件曝光同步的证明。前三条差值超过标称30帧/秒对应的约33.3毫秒单帧周期。

这些差值本身不证明静态室内取流失败，也不足以推断82帧的整体分布。可能原因包括缓存、时钟语义或配对实现，现有包未包含该适配器的配对代码。未来用于移动相机或风动茶芽前，应明确时间戳来源、缓存和预热规则，再按允许的像素错位制定时间差判据；不能直接沿用这个 `qc_pass` 字段作为动态数据验收。

彩色原图实际为室内天花板与灯具，节选却保留 `domain_tag=tea_garden_proxy`。索引已说明这一历史误标，原件不改。后续数据清单应另设经复核的场景类别，避免程序按旧字段自动把它计入茶园数据。

`calibration.json` 中两套内参相同、深度到彩色的旋转为单位阵、平移为零，与记录的“软件对齐后共同像素网格”描述相容；这不能证明物理双目基线为零，也不能替代独立标定。`valid=true` 只作为旧软件状态保留。现有包未包含产生这些参数的完整适配器，故不能进一步确认其物理来源。

## 4. 扫描程序可以复用到哪一层

上传的扫描程序用于白色夹爪搜索，只订阅彩色图并发送舵机指令。它可参考的部分是网格生成、逐步发令及保存记录；评分不是茶芽发现评分，评分排序不能当采集顺序。

扫描清单覆盖约37.269秒，各条时间戳不同，最小相邻间隔约1.260秒。但当前程序等待时只检查时间戳是否不同于发令前；等待超时后仍可能保存缓存图，未强制证明图像是在稳定结束后曝光。这里指出的是代码在未来异常情况下的缺口，不是判定这30条记录已经陈旧。

当前代码会写入 `raw_file`，已上传清单的30条记录都没有该字段，说明代码与清单之间还存在版本/生成流程待核项。清单也没有深度文件或标定后的相机位姿，不可直接作为彩深主动视角回放集。

四条静态坐标变换仅描述相机内部坐标系关系，没有提供基座、两条转轴到相机光心的完整运动链。不能仅凭舵机角度算出可靠的观察位置，也不能直接判定云台一定不能产生有效平移。先查安装结构、光心偏置和零位，再决定需要怎样的观察运动。

## 5. 四项档案哈希报错的纠正

对固定主分支提交直接读取 Git 对象，四份原件全部匹配 `archive/manifest.json`。在本轮常规检出中，全仓校验也通过。

在独立临时检出中开启 `core.autocrlf=true`，能准确复现四项 `Archive changed`。加入本次 `.gitattributes` 的字节保留规则并重新检出后，全仓校验通过，证据哈希仍为19/19。这支持换行转换是本机报错的可复现解释；没有读取用户电脑的实际 Git 配置，因此不将模拟原因写成已确认的本机唯一原因。

规则只针对历史原件、上传证据和生成的文献索引，避免自动换行改变被哈希的字节。已有本机检出可在保留未提交改动后另建干净检出验证；不要修改原始哈希清单迎合本机字节。

## 7. 复核入口

已安装 NumPy（数值计算库）和 Pillow（图像读取库）的环境中，可执行 `python tools/review_local_inventory.py`。脚本只读取上传文件、调用纯数值几何函数并输出复核记录，不导入机器人运行模块，不连接设备。重算的数值容差与两个候选阈值写在脚本中；它们用于定位复现缺口，不是新增现场验收门槛。

仓库结构检查仍使用 `python tools/validate_repository.py`。所有检查的范围均不包括新实验、完整82帧验证或原始点云重建。
